Claude Code vs. Codex: which agent actually finishes the job?

We gave both CLI agents the same nine tasks in the same deliberately messy repo and scored every round. The gap is real. It is just not where the marketing says it is.

The short version

Both agents are competent. Claude Code took the rounds that reward patience: long refactors, ambiguous bug reports, sticking to a rules file. Codex took the rounds that reward being wired into your forge. If your work lives in pull requests, that matters more than any benchmark.

Every comparison of coding agents I have read makes the same mistake: it tests them on a clean repo. Clean repos are not where these tools earn their keep. So we built the opposite, a 40k-line service with two competing HTTP clients, a test suite that fails intermittently, and a README that has been wrong since 2024, and pointed both agents at it.

Round 00How we tested

Nine tasks, run three times each per agent, in a fresh clone every time. Both agents got the same prompt text, the same instruction file content, and default settings otherwise. We logged wall-clock time, tokens, human interventions, and whether the change actually passed review from someone who did not know which tool produced it.

Scoring

A round goes to the agent whose output a blind reviewer would merge with fewer changes. Ties are real ties, not diplomacy. The task prompts and the seed repo are linked at the bottom so you can rerun any of this.

Round 01Cold start on an unfamiliar repo

The first thing an agent does in a strange codebase tells you most of what you need to know. We asked both to answer a plain question: where does rate limiting happen, and why does it not apply to the webhook route?

Codex went straight to grep, found three candidate files, and answered in about forty seconds. The answer was correct about the middleware and wrong about the reason: it named the wrong config flag. Claude Code took nearly three minutes, read the middleware and the route registration order, and produced an answer that traced the actual cause: the webhook router is mounted before the limiter.

Speed is a feature right up until the fast answer is wrong. In a repo you already know, Codex's approach is the better trade. In one you do not, the extra two minutes bought a correct answer.

Round 01 CCClaude Code

Slower, but it read the code instead of pattern-matching on filenames. On unfamiliar ground that is the whole game.

Round 02The multi-file refactor

The task: collapse two HTTP clients into one, keep both call signatures working, and do not touch the retry semantics. Eleven files. This is the round where agents usually fall apart, and the failure mode is always the same. They get eight files right and quietly break the ninth.

Codex finished first and left two call sites on the old client. Not broken, just not done, and nothing in its summary mentioned it. Claude Code worked through the list, checked back after the sixth file, and flagged one signature it could not preserve without a deprecation shim, which is exactly the judgment call you want surfaced rather than guessed at.

The agent to worry about is the one that stops early and reports success.

Round 02 CCClaude Code

Finished the whole list and said out loud what it could not do. Codex was faster to a partial result and framed it as complete.

Round 05Instruction files: does anyone read them?

Both tools support a repo-level rules file: CLAUDE.md for one, AGENTS.md for the other. We wrote the same eight rules into each and counted violations across all nine tasks.

CLAUDE.md 
# Rules the agent must not break

- Never edit files under `src/generated/` — they are rebuilt from protos.
- Tests go next to the file they cover, not in `__tests__/`.
- Use the repo logger. `console.log` fails CI.
- No new dependencies without asking first.
- Run `pnpm check` before you claim a task is done.

Across 27 runs, Claude Code broke a rule four times. Codex broke one eleven times, and nine of those were the same rule, the generated directory. Neither is perfect. One is noticeably more governable.

Rules only work if they are testable

Both agents obeyed short, checkable rules far more reliably than aspirational ones. "Never edit src/generated/" held up. "Write clean, idiomatic code" was ignored by both, every time.

Round 05 CCClaude Code

Roughly a third of the violation rate on identical rules. If you have a house style you actually enforce, this round is worth more than it looks.

Round 07The round Codex wins outright

Here is where the story flips. Ask for a change that ends in a reviewable pull request (branch, commit, description, linked issue) and Codex is simply built for it. It opens the PR, writes a description a human would recognise as a description, and the whole thing lives where your team already reviews code.

Claude Code can do all of this too, and does it well from the terminal. But it is doing it as a sequence of git commands you asked for, not as a native motion. The difference shows up when you are handing work to teammates who are never going to open a terminal to see it.

CCClaude Code is better when

  • You are in the repo, in a terminal, right now
  • The task is ambiguous and needs judgment
  • You have a rules file you want obeyed
  • The change spans many files and must be complete
  • You want to see and approve each step

CXCodex is better when

  • The unit of work is a pull request
  • You want to fire off work and walk away
  • Teammates review in the browser, not the CLI
  • The task is well-specified and mechanical
  • You are running many small jobs in parallel
Round 07 CXCodex

Not close. If your team's unit of work is the pull request, this single round may outweigh the five that went the other way.

So which one should you use?

The honest answer is that the scoreline is not the recommendation. Five to three is close, and the three rounds Codex won are all the same round wearing different hats: it is better at handing work off. The five Claude Code won are also one round: it is better at finishing work carefully.

So pick on that axis, not on the total. If you sit in the repo and care that the change is right, Claude Code. If you dispatch work and review it later in a browser, Codex. Plenty of teams should run both, and the split is not subtle: exploratory and ambiguous work in the terminal, well-specified mechanical work in the forge.

Shelf life

This was run in August 2026. Both tools ship weekly and at least two of these rounds will be stale within a quarter. The seed repo and task prompts are published so you can rerun it against whatever is current when you read this.

Frequently asked

Did you use the same model for both?

No, and you cannot. Each tool runs its vendor's own models. That is part of what is being compared. We used each tool's default model with default reasoning settings, which is what most people run.

Isn't a 40k-line repo too small to be representative?

For the refactor and debugging rounds, yes, it is on the small side. We picked it because we could verify every result by hand. A larger repo would widen the gap in rounds 1 and 2, based on spot checks we did not score.

Why not include Cursor, Windsurf or the rest?

Different shape of tool. Editors and CLI agents fail in different places and comparing them in one table flatters both. The editor comparison is a separate teardown.
